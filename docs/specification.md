イベント会計支援サイト　「会計くん」　仕様書
最終更新　2026/10/12

# 背景
あるサークルでは文化祭で例年喫茶店を出しており、そのレジでは会計用のエクセルを作成し、それに入力（ボタン操作が主）をすることによってマクロが作用し売り上げの集計がなされる仕組みだった。しかし、シートを毎年作成し、マクロとボタン入力を用意するのは労力がかかる。そこで会計用シートの作成を支援するwebサイトを作る。将来的にはweb上で会計処理の入力もできるようにしたいが、文化祭の模擬店というネットワークの不安定な環境を前提にするため、データベースとなるのは表計算ソフトのあるシートとし、オフラインの表計算ソフト上でも稼働するようにする。

# 概要
webサイト上で販売する商品と価格、仕入れ情報の一覧を入力すると、「会計用シート」「売上履歴」「売上統計」の３枚のシートを持つGoogleスプレッドシートが作られ、それをダウンロードすることが出来る。


## 会計用シート
会計とデータ手動入力用のシートである。
各列には以下の情報が表示される。

A列:品目
B列:単価
C列:個数
D列:個数マイナスボタン
E列:個数プラスボタン

1A,1B,1Cには商品の情報はなく、見出しとして「品目」「単価」「個数」と表示させる。
ボタンはマイナスボタンは青色、プラスボタンは赤色で、それぞれ-,+と表示されている。これらのボタンを押すことでその行の品目の個数を1ずつ増減させることが出来る。

F列は空白で、G5に「合計」の文字、H6に入力された単価×個数の総和（つまり合計金額）が表示される（これにはスプレッドシートの関数かマクロを用いる）。G2,H2,G3,H3にまたがって「会計」のボタンが置かれていて、このボタンを押すとすべての個数が0になり、入力された情報は一回の会計として他のシートにデータとして記録される。

## 売上履歴
会計用シートの会計ボタンが押されると、その会計の情報がマクロによって自動入力される。
全ての売り上げが記録される。基本的に人間の手による入力を想定しない（そのような設定にできるとなおよい）
各列には以下の情報が表示される。

A列:会計時刻
B列:売上品目
C列:売上高

1A,1B,1Cには商品の情報はなく、見出しとして「時刻」「売上品目」「売上高」と表示させる。

売上品目は「(品目名)×(個数)」を「,」で結合した文字列とする。
例えばコーヒー２杯とワッフルを売り上げた場合、「コーヒー×2,ワッフル×1」と記録される。

## 売上統計
売り上げの統計を見ることができる。
会計用シートの会計ボタンが押されると、その会計の情報がマクロによって自動集計される。
各列には以下の情報が表示される。

A列:品目
B列:単価
C列:売り上げ個数
D列:在庫数量

E列は空白で、F2に「総売上高」の文字、G3に単価×売り上げ個数の総和（つまり売り上げ金額）が表示される。

# 今後の展望
webサイト上からでも会計の入力ができるようにしたい。シート状の入力では、ボタンが押しずらい、どのボタンでどの項目が増えるのかわかりずらいなどの問題があり、それをサイト上で見やすいUIの下でそうできるようにする。
ボタンの扱いとしては変わらず、サイト上で個数を増減させると会計用シートの個数がそれに伴って増減、会計ボタンを押すことでシート状の会計ボタンを押したときと同じように処理が行われるのが理想。

- webサイト上から作成、編集することがエクセルよりも容易であると考えられることから今回はスプレッドシートを用いることにしている。しかしそもそもwebサイト上でスプレッドシートのファイルを新規作成、編集をすることは可能か
- webサイト上からスプレッドシートが作成、編集可能であるとして、スプレッドシート上で動くマクロ付きのものを生成することは可能か。
- webサイトからの読み書きに関してエクセルではライセンスの設定が必要か。
- ライセンスの設定が必要でないならエクセルとスプレッドシートのどちら対応させるべきか、両対応可能か
- ボタンをスプレッドシートに追加するのは機械的にwebサイトから出来るか

# 設計評価・疑問への回答（2026/10/12追記）

この追記は、上記の原案に対する評価と提案である。提案は未確定であり、元の仕様を置き換えるものではない。公式ドキュメントとライブラリの公式資料を確認した範囲で評価し、プログラム・マクロ・試作ファイルは作成していない。

## 1. 総合評価

**商品情報から会計用の表計算ファイルを生成する構想は実現可能。ただし、Googleスプレッドシートのマクロをダウンロード先でも動かす想定は成立しない。オフライン会計を必須とするなら、出力形式と実行環境を先に決める必要がある。**

背景にある「毎年ボタンやマクロを作り直す手間を減らす」という目的は明確で、商品・価格を差し替える共通テンプレート方式と相性がよい。会計画面、履歴、統計を分ける構成も、小規模な模擬店には理解しやすい。

一方、Googleスプレッドシートのオフライン編集と、Apps Scriptによる会計処理のオフライン実行は別である。Apps ScriptはGoogleのサーバー上で実行されるため、ネットワークがない状態で増減ボタン・会計確定処理を動かす基盤にはできない。これは公式の実行方式からの設計上の判断である。［[Apps Scriptの実行環境](https://developers.google.com/apps-script/guides/services)、[Sheetsのオフライン編集](https://support.google.com/docs/answer/6388102?hl=ja)］

| 要件 | 評価 | 条件・注意点 |
| --- | --- | --- |
| Webから商品・価格を入力し、3シートを作成 | 実現可能・比較的容易 | Google APIによる作成と、Excel形式の直接生成の両方が候補 |
| 合計金額の表示 | 実現可能・容易 | 標準の表計算関数で対応可能 |
| 増減ボタン、会計履歴への追記 | 実現可能・中程度 | Google版はApps Script、Excel版はVBAなど、実行環境別の処理が必要 |
| Google版をダウンロードして、そのままオフラインでボタンを使用 | 原案の方式では不可 | Apps ScriptはExcel用VBAへ自動変換されない |
| Excelデスクトップ版でオフライン会計 | 実現可能・中程度 | `.xlsm`、対応Excel、マクロ実行許可、保存処理が必要 |
| Web画面からオンラインで会計入力 | 実現可能・中程度 | 認証、確定処理、通信失敗・二重記録への対策が必要 |
| Web画面からオフラインで会計し、後で同期 | 実現可能・難度が高い | 端末内保存と同期設計が必要。シートだけを唯一の保存先にはできない |
| 複数レジでオフライン会計し、在庫を厳密に共有 | 制約が大きい | 切断中の他端末の販売は分からない。端末別の在庫割当などが必要 |

## 2. 疑問への回答

### Q1. WebサイトからGoogleスプレッドシートを新規作成・編集できるか

**可能。** Google Sheets APIでファイル作成、シート追加、セルの値・数式・書式などを操作できる。Google Drive APIを併用すればテンプレートファイルのコピーや対応形式への書き出しも可能。［[作成API](https://developers.google.com/workspace/sheets/api/guides/create)、[更新API](https://developers.google.com/workspace/sheets/api/guides/batchupdate)、[書き出し形式](https://developers.google.com/workspace/drive/api/guides/ref-export-formats)］

ただし、利用者のGoogle Drive内に作成するなら、その利用者のログインと必要なアクセス権の承認を設計する。サイト側の管理アカウントで作成する方式なら、所有者・共有先・翌年への引継ぎを決める必要がある。「Webから編集しやすい」という理由だけで、Excelファイル生成より必ず容易になるわけではない。［[Google OAuth](https://developers.google.com/identity/protocols/oauth2/web-server)］

また、Googleスプレッドシートはクラウド上の文書である。「作成したクラウド文書へのリンクを渡す」のか「Excel等のファイルをダウンロードさせる」のかを概要で区別した方がよい。

### Q2. Googleスプレッドシート上で動くマクロ付きのものを生成できるか

**オンラインで動くApps Script付きのシートなら可能。** Google版のマクロはApps Scriptであり、ExcelのVBAとは異なる。［[Googleのマクロ](https://support.google.com/docs/answer/9331168?hl=ja)］

候補は次の2方式。

- **テンプレートをコピーする方式：** あらかじめ共通の会計処理を持つシートを用意し、イベントごとにコピーして商品情報を設定する。コンテナに紐づくスクリプトもコピーされる。商品数が変わる場合のボタン配置や、初回の実行承認は別途考慮する。［[シートに紐づくスクリプト](https://developers.google.com/apps-script/guides/bound)］
- **APIでスクリプトも作成する方式：** Apps Script APIの`projects.create`に親ファイルIDを指定し、`projects.updateContent`で処理を登録する。Sheets APIだけで完結する方式ではなく、追加の権限・設定が必要になる。［[プロジェクト作成](https://developers.google.com/apps-script/api/reference/rest/v1/projects/create)、[内容更新](https://developers.google.com/apps-script/api/reference/rest/v1/projects/updateContent)］

**このGoogle版をExcelへ書き出しても、オフライン会計用マクロにはならない。** GoogleのExcel向け書き出し形式は`.xlsx`で、VBAを含む`.xlsm`とは別である。Apps ScriptとVBAの互換性を前提にせず、Excel用処理は別に用意する。［[書き出し形式](https://developers.google.com/workspace/drive/api/guides/ref-export-formats)、[Excelマクロ形式](https://xlsxwriter.readthedocs.io/working_with_macros.html)］

### Q3. WebサイトからExcelを読み書きするにはライセンス設定が必要か

**Excel形式のファイルを扱うことと、ExcelアプリやMicrosoftのクラウドを操作することを分けて考える。**

| 方式 | ライセンス・認証に関する整理 |
| --- | --- |
| ライブラリで`.xlsx`／`.xlsm`を生成・編集し、ダウンロードさせる | Excelアプリを起動しない方式なら、生成処理のために利用者のMicrosoftログインやExcelのライセンスキーをサイトへ設定する必要はない。ライブラリごとの対応範囲・利用条件は確認する |
| 利用者がファイルをExcelデスクトップ版で開き、VBAを実行する | その端末でExcelを利用できるライセンスと、マクロを許可できる環境が必要 |
| OneDrive／SharePoint上のブックをMicrosoft Graphで操作する | Microsoft側のアカウント・保存先・アクセス権が必要。契約や学校アカウントの利用条件を確認する。ローカルファイル生成とは別の設計 |

Excelファイルの生成例として、XlsxWriterの公式資料には既存のVBAを組み込んだ`.xlsm`とボタンの生成方法がある。ただし同ライブラリは既存ファイルの読込み・編集用ではないため、生成と読込みではライブラリ選定が異なる。GraphのExcel APIは業務用OneDrive／SharePoint等のブックを対象とし、個人用OneDriveは現時点の公式資料では非対応である。［[XlsxWriterのマクロ生成](https://xlsxwriter.readthedocs.io/working_with_macros.html)、[XlsxWriter FAQ](https://xlsxwriter.readthedocs.io/faq.html)、[GraphのExcel API](https://learn.microsoft.com/en-us/graph/api/resources/excel?view=graph-rest-1.0)］

この用途では、まず「サイトでファイル生成 → ダウンロード → 手元のExcelで使用」とすれば、Microsoftのクラウド連携を初期段階で設ける必要はない。

### Q4. ExcelとGoogleスプレッドシートのどちらに対応すべきか。両対応は可能か

**当日のオフライン会計を最優先し、利用端末にExcelがあるなら、最初はExcelデスクトップ版向けの`.xlsm`を推奨する。** これは原案の要件に基づく提案であり、利用端末とライセンスは未確認。

| 観点 | Excelデスクトップ版＋VBA | Googleスプレッドシート＋Apps Script |
| --- | --- | --- |
| ネットなしでボタン会計 | 対応可能 | Apps Scriptによる処理は不可 |
| 利用環境 | 対応Excelとマクロ実行許可が必要 | オンライン環境、Googleアカウント等が必要 |
| Webからの生成 | 直接ファイル生成が可能 | API作成・テンプレートコピーが可能 |
| 共有・同時閲覧 | ローカル運用では共有方法を別途決める | オンライン共有に向いている |
| 初期の運用上の注意 | ダウンロードしたマクロのブロック、端末差、ファイル保存 | 初回承認、通信遅延、APIの利用上限 |

ExcelのWeb版ではVBAを実行できないため、「Excel対応」とだけ書かず、対応OS・デスクトップ版・バージョンを明記する。Windowsでダウンロードしたマクロ付きファイルは、Officeの設定や組織ポリシーによって実行がブロックされる。文化祭前に実機で確認する工程が必要。［[Excel Web版のVBA制約](https://support.microsoft.com/en-us/excel/work-with-vba-macros-in-excel-for-the-web)、[ダウンロードしたマクロの制約](https://learn.microsoft.com/en-us/microsoft-365-apps/security/internet-macros-blocked)］

**両対応も可能だが、単一のマクロを両方で使う方式にはできない。** 商品・取引の項目と計算ルールは共通化し、出力と会計処理をExcel版／Google版で分ける。検証する環境が増えるため、初期版から両方を完成させるより、一方を安定させてから追加する方が現実的。

Excelを使える端末がない場合は、Google版がオフライン要件を満たすわけではない。後述のオフライン対応Webアプリ、または別のローカル表計算ソフト向けの方式を検討する。ExcelのVBAが他の表計算ソフトでもそのまま動くとは保証しない。

### Q5. ボタンを機械的に追加できるか

**可能。ただし、セルを色付けするだけではクリック処理は付かない。**

- **Google版：** Apps Scriptでセル上に画像を配置し、`OverGridImage.assignScript`で関数を割り当てる方法がある。ボタンに見える画像を用意すれば、配置と処理の紐づけを自動化できる。ただし画像・図形によるスクリプト実行はWebブラウザでのクリックが対象で、モバイル上のクリックでは実行されない。［[画像への関数割当](https://developers.google.com/apps-script/reference/spreadsheet/over-grid-image)、[画像・図形からの実行制約](https://developers.google.com/apps-script/guides/menus)］
- **Excel版：** 既存のVBAを埋め込み、マクロを割り当てたボタンを生成する方法がある。例えばXlsxWriterはボタン追加に対応するが、すべてのコントロールや見た目に対応するわけではない。青・赤などの厳密な外観は、テンプレートや図形を含めて別途検討する。［[マクロとボタンの生成](https://xlsxwriter.readthedocs.io/working_with_macros.html)］

商品数に応じた配置、並べ替え後も正しい商品に作用する紐づけ、連打時の扱いを仕様に追加する。Google版では関数名を割り当てる仕組みなので、行番号などの引数を直接渡せる一般的なWebボタンと同じには扱わない。

## 3. 現状の設計で修正・明確化したい点

以下は設計上の提案である。表計算ソフトの選定にかかわらず、会計記録を信頼できる形にするために重要。

### 3.1 売上履歴は表示用文字列だけを保存しない

「コーヒー×2,ワッフル×1」は人が読む表示には適しているが、集計の唯一の元データにするのは避けたい。商品名に`,`や`×`が入ると解釈が曖昧になり、名称変更や価格変更にも弱い。

推奨する保存項目は、取引単位の「取引ID、確定時刻、合計額、状態」と、商品明細単位の「取引ID、商品ID、会計時点の商品名、会計時点の単価、数量、明細金額」。取引IDで複数の明細を同じ会計に結びつける。現在のA〜C列は見やすい一覧として残し、集計用明細を別領域または追加シートに持つ案がよい。3枚に限定する場合も保存領域を明記する。

### 3.2 統計は「現在の単価×累積個数」で総売上を求めない

途中で価格を変更すると、過去の売上まで現在の単価で計算される。例えば100円で2個販売後、単価を120円に変更すると、原案の計算では売上が240円になってしまうが、実売上は200円である。

総売上高は、会計時点の金額を固定して記録した履歴から集計する。販売数量も履歴から再計算できるようにし、マクロで累計セルだけを増やす方式に依存しない。履歴を正本、統計を再生成できる表示とする。

### 3.3 会計確定と保存の順序を定義する

会計ボタンは、入力検証 → 取引IDの決定 → 明細・金額の記録 → 保存成功の確認 → 個数リセット、の順を基本とする。保存に失敗した場合は入力を残し、成功したように見せない。Excelではセルへの追記とディスクへの保存は別なので、確定時にブックを保存するかを決める。

空の会計、負数、小数、文字列の数量は拒否し、連打・再送で同じ取引が二重記録されないようにする。処理中は確定操作を抑止し、通信の応答が失われた場合は同じ取引IDで記録済みか確認する。履歴の記録と入力リセットの途中で処理が止まった場合も、そのIDを基に回復できる設計にする。

Google Sheets APIの単一のバッチ更新には原子的な適用の仕組みがあるが、複数API呼出しや複数端末による会計全体の整合性を自動で保証するものではない。更新手順と重複対策は別途必要。［[バッチ更新の保証範囲](https://developers.google.com/workspace/sheets/api/guides/batch)］

### 3.4 取消・訂正を用意する

個数リセット前の注文取消と、会計確定後の売上取消は区別する。確定後は元の履歴を削除するより、元取引IDを参照する取消記録を残し、売上と在庫への反映ルールを定める。返品で商品が戻る場合と、注文誤入力・廃棄の場合では在庫の扱いが異なる。初期版は「全取引の取消のみ」などに範囲を絞ってもよい。

### 3.5 仕入れ・在庫の定義が不足している

概要には仕入れ情報の入力があるが、保存項目と在庫の計算方法がまだない。初期版は完成品単位の在庫として「初期在庫＋追加仕入れ＋再販売可能な返品−販売数量−廃棄等」を定義する案を推奨する。在庫を管理しない商品も指定できるとよい。

コーヒー豆や牛乳などの材料在庫まで扱う場合は、商品1個に必要な材料量・単位・仕込み・廃棄の管理が必要になり、難度が上がる。売上集計、利益計算、材料管理を初期版の同じ範囲に含めるかは分けて判断したい。仕入れ金額を記録するだけで、売れ残り等も考慮した利益が正確に出るとは限らない。

### 3.6 履歴保護と実行権限を両立させる

履歴・数式の保護は誤操作対策として有用。ただし、手入力を禁止したユーザーの権限でマクロ／スクリプトを実行すると、その処理も履歴に書けない構成があり得る。管理者だけが訂正できる範囲、処理の実行権限、所有者の引継ぎを決める。保護や非表示だけで改ざん防止を保証するものにはしない。

### 3.7 当日の操作と運用条件を補う

- 数量は0以上の整数、金額は日本円の整数を初期案とし、販売価格を税込の最終価格とするかを明記する。割引・セット価格の有無も決める。
- 会計時刻は確定時の固定値とし、タイムゾーンを`Asia/Tokyo`に統一する。Excelのオフライン運用では端末時計に依存するため、事前に時計を確認する。
- 会計時に金銭授受も支援するなら、預り金とお釣りの入力・表示を追加する。売上記録だけを目的にするなら、その範囲を明記する。
- ボタンは色に加えて`−`／`＋`と商品名との対応を明確にし、十分な大きさを取る。商品数が多い場合のスクロールと合計・確定ボタンの見やすさを検討する。
- 「1A」は通常のセル表記では「A1」。表示位置もG5とH6、F2とG3で行がずれているので、意図した配置か確認する。レイアウト位置と記録処理の参照先を切り離すと、翌年の変更が容易になる。
- 当日の担当端末、商品数・取引件数の想定、バックアップ間隔、終了後の照合方法を決める。クラウド保存・自動保存という名称だけで、会計確定の保存保証があるとはみなさない。

## 4. 今後の展望の実現可能性

### 4.1 オンラインのWeb会計画面

実現可能。ただし、数量ボタンを押すたびにシートへ通信するより、**入力中の注文は画面内に保持し、会計確定時にまとめて履歴へ送る**方式を推奨する。毎回通信すると回線の遅延がボタンの応答に影響し、共有の「個数」セルは複数レジの注文が混ざる原因になる。Sheets APIには利用上限もある。［[Sheets APIの利用上限](https://developers.google.com/workspace/sheets/api/limits)］

原案の「画面と会計用シートの個数が常時一致」は、単一レジ・オンライン限定なら実現できるが、必須にしない方が拡張しやすい。必要なら端末ごとに注文の保存領域を分け、シートを編集する操作とWebでの入力を同時に行わないルールを設ける。

また、APIでセルを更新しても`onEdit`は自動発火しないため、「Webがセルを書き換えれば、既存のマクロが会計まで進める」という設計にはできない。Webとシート内ボタンから、同じ会計確定処理を明示的に呼び出す構成を検討する。Webからシート画面上のボタンを物理的に押す必要はない。［[トリガーの制約](https://developers.google.com/apps-script/guides/triggers)］

Apps ScriptのWebアプリも候補になるが、所有者権限で実行するか利用者権限で実行するかでアクセス範囲が変わる。会計入力を許可する利用者と対象シートを制限する設計が必要。［[Apps Script Webアプリ](https://developers.google.com/apps-script/guides/web)］

### 4.2 オフラインのWeb会計画面

技術的には実現可能。Service Workerで画面を事前に保存し、IndexedDBで端末内に取引を保存する構成が候補になる。事前のオンライン準備、対応ブラウザ、保存容量・データ消去への対策、実機検証が必要。画面をキャッシュするだけでは会計データの保存機能にはならない。［[Service Worker](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API)、[IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API)］

ただし、この方式では**通信断中の正本は端末内の取引記録**になる。クラウドのシートは再接続後の同期先・集計先となるため、「常にシートだけがデータベース」という前提は変更する必要がある。

必要な仕様は、端末をまたいで重複しない取引ID、未同期件数の表示、同じIDを再送しても一度しか登録しない仕組み、同期失敗時の再試行、データの書き出し・復旧である。「端末内に保存済み」と「クラウドにも同期済み」は画面上で区別する。

複数端末が切断中に同じ在庫を販売すると、全端末の最新在庫は共有できない。初期段階では1台で運用するか、端末別に販売可能数量を割り当てる。複数レジでの厳密な在庫管理や同時更新が必要になった時点で、シートを集計・出力先にし、専用の保存基盤を正本とする構成も検討する。

### 4.3 Webから手元のExcelへ直接連動

Google Sheets APIやMicrosoft Graphは、手元で開いているローカルExcelを直接操作するものではない。通常のWebページが任意のローカルファイルを無断で継続編集することも前提にできない。ファイルアクセスにはブラウザの対応範囲やユーザーの選択が関わり、ファイル書込みができてもExcelのVBA実行と同じではない。［[ブラウザのFile System API](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API)］

そのため、最初は「WebとExcelを同時に連動させる」より、運用中の入力先を一つに限定するのが現実的。Excelで会計した履歴を終了後に取り込む方式、またはWebで会計して履歴を表計算ファイルへ出力する方式を候補とする。同じイベントのファイルを別々に編集するなら、単純な上書きではなく取引IDによる統合が必要になる。

## 5. 推奨する進め方と未決事項

原案のオフライン要件と既存のExcel運用を優先する場合の提案は次の順序。

1. **利用環境と記録ルールを確定する。** Excelデスクトップ版の有無、OS、1台／複数台、在庫の対象、取消・価格変更・保存の扱いを決める。
2. **初期版はWebで設定し、Excel用`.xlsm`を生成する範囲に絞る。** 共通の会計処理を毎年再利用し、商品・価格・初期在庫だけ差し替える。初期版ではローカルExcelを会計記録の正本とする。
3. **Google版が必要ならオンライン専用として追加する。** 同じ商品・取引の定義を使い、Apps ScriptとGoogle向けの操作部分を別に用意する。
4. **Web会計はまず単一端末で設計する。** オフライン対応する段階で端末内保存と同期の仕様を追加し、正本の所在を明確にする。複数レジ対応はその後の別段階とする。

実装前に決めたい事項：

- 当日使う端末・OS・Excelの種類と、学校等のマクロ制限は何か。
- 完全に通信なしでも会計を続ける必要があるか。レジは何台か。
- 在庫は完成品だけか、材料まで管理するか。仕入れ原価・利益集計も初期版に含めるか。
- 割引、価格変更、取消、返品、売切れ時の確定禁止をどこまで扱うか。
- 3シートは画面構成の希望か、補助シートも含めた厳密な上限か。
- 年ごとの商品設定を再利用する方法と、保存データを翌年の担当者へ渡す方法は何か。

将来の実装後に行う受入確認としては、通信を切った状態での会計・保存・再起動、連打や保存失敗時の履歴保全、取消後の売上と在庫、価格変更前後の集計、生成したファイルの実機でのマクロ実行を含める。Web同期を追加した際は、同じ取引の再送と通信断からの復旧を確認する。今回の評価ではこれらの実装・実測は行っていない。
